---

## 0. 怎么用这份文档

这里写的是**依赖顺序**，不是时间表。原则只有一条：

> 上一个阶段的门禁没过，不进入下一个阶段。

因为返工成本不对称：权限做错要在每个接口补；状态机做错要改所有页面；表结构做错要重写迁移。**先做“错了代价最大”的部分**，是这份路径的排序依据。

每个阶段都包含五块：目标、产出、步骤、**验证门**、**返工信号**。返工信号比验证门更重要——它告诉你什么时候该停下来重做，而不是继续往上堆。

## 1. 路径总览

```
P0 决策冻结
   │  技术栈、认证方式、版本号定死，不再讨论
   ▼
P1 骨架与数据      M1   应用能起、表能建、页面能读库
   ▼
P2 身份与权限      M2   登录、角色、数据范围、越权拦截
   ▼
P3 业务闭环        M3   状态机、7 个动作、回复、事件、并发
   ▼
P4 质量与交付      M4   测试、CI、镜像、部署
   ▼
P5 版本演进        V1.1 / V1.2 / V2   按触发条件启动
```

阶段之间是**硬依赖**，不是建议：

| 跳过的后果 | 说明 |
| --- | --- |
| P1 没做完就做 P2 | 表结构还在变，迁移文件会互相打架 |
| P2 没做完就做 P3 | 每个动作端点都要回头补权限判断 |
| P3 没做完就做 P4 | 没有稳定业务逻辑，测试写了也要重写 |
| P4 没做完就加 AI | 出了问题分不清是模型还是系统 |

## 2. P0 决策冻结

**目标**：把“还在选型”的状态结束掉。选型阶段每多一天，都是在为同一个问题反复付费。

### 产出

一张冻结清单，写进 `02-design.md` 的版本记录里：

| 项 | 冻结值 |
| --- | --- |
| 运行时 | Java 21 |
| 框架 | Spring Boot 4.1.x |
| 持久层 | MyBatis（starter 4.1.x，对应 Boot 4.1.x） |
| 数据库 | MySQL 8.4 LTS |
| 迁移 | Flyway（含 `flyway-mysql`） |
| 页面 | Thymeleaf（服务端渲染） |
| 认证 | Spring Security 表单登录 + Session |
| 构建 | Maven + Wrapper |
| 模块 | 单 Maven 模块，功能分包 |

### 验证门

- [ ] 上述九项没有一项写着“待定”
- [ ] 认证方式已从“待确认”转为正式决定
- [ ] 版本号写的是具体版本，不是 “latest”

### 返工信号

- 又在比较 JPA 和 MyBatis → 停，本题已结案
- 想同时支持两种数据库 → 停，MVP 不支持

## 3. P1 骨架与数据（对应 M1）

**目标**：一个能启动、能连库、能从数据库读出数据的空壳。

### 产出

- 可运行的 Spring Boot 工程（`pom.xml`、`mvnw`）
- `compose.yaml`（MySQL 8.4）
- `V1__init.sql`（7 张表）、`V2__seed.sql`（org + 分类）
- 5 个实体类、1 个 Mapper 接口 + XML
- `GET /tickets` 列表页

### 步骤

| # | 做什么 | 做完的标志 |
| --- | --- | --- |
| 1 | 用 Initializr 生成工程，补 MyBatis 与 `flyway-mysql` 依赖 | `./mvnw spring-boot:run` 能启动 |
| 2 | 写 compose，起 MySQL | `docker compose ps` 显示 healthy |
| 3 | 配数据源与 MyBatis | 应用启动不报连库错误 |
| 4 | 写 `V1__init.sql`，启动应用 | `show tables` 得到 7 张表 |
| 5 | 写实体 + `TicketMapper.findAll` | 单元测试或临时接口能查出数据 |
| 6 | 写列表页 | 浏览器能看到工单标题 |
| 7 | 首次提交 | `git log` 有一条完整提交 |

### 验证门

- [ ] `docker compose ps` → healthy
- [ ] `show tables` → 正好 7 张
- [ ] `GET /tickets` → 200，页面有数据
- [ ] `git status` → 干净，`target/` 未入库

### 返工信号

- 开始调 CSS、加导航栏 → 停，这是 P3 之后的事
- Controller 里出现 SQL 字符串 → 停，下沉到 Mapper
- 手工在数据库里改表结构 → 停，改迁移文件并重建

## 4. P2 身份与权限（对应 M2）

**目标**：没有登录什么都看不到；三种角色看到的数据范围不同；越权被后端拦住。

### 产出

- `SecurityConfig`（表单登录、放行规则、登出入口）
- `DbUserDetailsService`
- 注册页 + 校验
- 列表查询的角色范围过滤
- `/admin/users` 最小管理页
- 越权测试用例

### 步骤

| # | 做什么 | 做完的标志 |
| --- | --- | --- |
| 1 | 开启表单登录，所有业务路径要求认证 | 未登录访问 `/tickets` 跳登录页 |
| 2 | 用户改为从数据库读取，角色映射成 `ROLE_*` | 数据库里的用户能登录 |
| 3 | 注册页 + 用户名唯一校验 | 重复用户名返回明确错误 |
| 4 | 列表按角色过滤 | `REPORTER` 看不到他人工单 |
| 5 | 详情页归属校验 | 访问他人工单 403 |
| 6 | 管理员用户页 | 能改角色、能停用 |
| 7 | 写越权测试 | 测试能在 CI 里跑 |

### 验证门

- [ ] 未登录 → 302 `/login`
- [ ] 三种角色看到的列表条数符合预期
- [ ] 越权访问返回 403，响应体与“不存在”一致
- [ ] 数据库里密码是 BCrypt 哈希，不是明文
- [ ] 停用用户无法登录

### 返工信号

- Controller 里出现 `if (currentUser.getRole() == ...)` → 停，下沉到 Service
- 模板里用 `th:if` 来决定“能不能看”而不是“要不要显示” → 危险，权限必须在服务端
- 每次加接口都要单独补一段权限代码 → 说明没有统一的归属校验方法

## 5. P3 业务闭环（对应 M3）

**目标**：一条工单能从创建走到关闭，且每一步都留下痕迹。

这是整个项目最重的一段，拆成四个子阶段，每个子阶段单独过门。

### 5.1 先做状态机（不做页面）

| 做什么 | 标志 |
| --- | --- |
| 写 42 种组合的参数化测试 | 测试先红 |
| 实现转移表与 `require` / `isAllowed` | 测试全绿 |
| 故意删一条转移，确认测试会红 | 证明测试有效 |

**门**：`TicketStateMachineTest` 全绿；删掉任意一条合法转移，测试必须失败。

### 5.2 再做动作端点

| 做什么 | 标志 |
| --- | --- |
| 按“五步法”实现 7 个动作 | 每个动作都能改变状态 |
| 写事件 | `ticket_event` 条数与动作数一致 |
| 非法跳转 | 返回 409，状态不变 |

**门**：对 `CLOSED` 工单调 `accept` → 409；直接改数据库状态绕过接口的测试必须失败（说明校验在服务端）。

### 5.3 再做回复与详情页

| 做什么 | 标志 |
| --- | --- |
| 公开回复 / 内部备注 | 两种都能写入 |
| 内部备注过滤在 SQL 层 | `REPORTER` 的查询结果里根本没有内部备注 |
| 详情页拼装 | 字段、动作按钮、回复流、时间线齐全 |

**门**：用 `REPORTER` 账号查详情，返回的 HTML 里搜不到内部备注的正文。

### 5.4 最后做并发与场景走查

| 做什么 | 标志 |
| --- | --- |
| 乐观锁冲突处理 | 两个窗口同时接单，一个成功一个提示冲突 |
| 场景 A–D 手工走查 | 四个场景全部顺畅 |
| 边界：处理人停用后转交 | 管理员能转交 |

**门**：场景 A–D 各走一遍并录屏/截图；冲突场景有明确提示，不是白屏。

### 整段返工信号

- 状态判断出现在 Controller、模板或前端 JS → 停
- 事件写入和状态更新不在同一事务 → 停（会出现“改了没记录”）
- 每个动作端点各写一遍“查工单 → 判归属 → 判状态” → 抽公共方法，否则第 8 个动作必漏
- 页面按钮和后端规则各写一份 → 必须共用 `isAllowed`

## 6. P4 质量与交付（对应 M4）

**目标**：别人能在一台干净机器上把它跑起来。

### 步骤

| # | 做什么 | 做完的标志 |
| --- | --- | --- |
| 1 | Testcontainers 集成测试跑完整链路 | `./mvnw verify` 全绿 |
| 2 | GitHub Actions | push 后 CI 绿 |
| 3 | 多阶段 Dockerfile | 镜像能构建 |
| 4 | 生产 compose（app + db） | 一条命令起全栈 |
| 5 | 部署到一台机器 | 公网/局域网可访问 |
| 6 | 重启验证 | 数据还在 |
| 7 | README | 新人照着能跑起来 |

### 验证门

- [ ] `./mvnw verify` 全绿（不是 `-DskipTests`）
- [ ] CI 在 PR 上也会跑
- [ ] 干净机器：`docker compose up -d --build` → `{"status":"UP"}`
- [ ] `docker compose restart app` 后数据仍在
- [ ] 仓库里搜不到密码、令牌、私钥

### 返工信号

- 测试只在本地过，CI 挂 → 环境差异，先统一版本
- 部署要手工执行 SQL → Flyway 没接上
- README 写成了架构文档 → 读者是“想跑起来的人”，先给命令

## 7. P5 版本演进（有触发条件才启动）

| 版本 | 触发条件 | 启动后第一件事 |
| --- | --- | --- |
| V1.1 通知/附件/SLA | 真实用满一周，且有人说“我不知道有回复” | 先做通知，附件最后 |
| V1.2 AI 分诊 | 工单量 > 200，且分类经常填错 | 先用规则+关键词做基线，再上模型对比准确率 |
| V2.0 多租户 | 出现第二个愿意付费的客户 | 先定隔离策略（共表 vs 独立库），再动表 |

**原则**：没有触发条件就不做。提前做等于给不确定的需求付确定的成本。

## 8. 每个阶段共用的四件事

1. **读**：先读官方文档对应章节，再读一个开源项目的对应实现。
2. **写**：一次只写一个可验证的小块，写完立刻跑。
3. **验**：用本阶段的验证门检查，不靠“看起来对了”。
4. **记**：提交信息写“为什么”；遇到坑记进 `03-build-guide.md` 第 6 节。

### 配套阅读（按阶段）

| 阶段 | 官方文档 | 开源实现参考 |
| --- | --- | --- |
| P1 | Spring Boot 入门、MyBatis 集成 | petclinic 的分层；RealWorld 的 `ArticleMapper.xml` |
| P2 | Spring Security 表单登录 | RuoYi 的 `SecurityConfig` 与 `@PreAuthorize` 用法 |
| P3 | 无（领域逻辑靠自己） | RealWorld 的 `ArticleCommandService` 与异常处理 |
| P4 | Testcontainers、Spring Boot 测试 | petclinic 的测试目录结构 |

### 读开源代码的方法

1. 先看目录，判断它按什么分包（这决定你能不能快速找到东西）；
2. 再看接口，不看实现（接口暴露设计意图）；
3. 最后看测试（测试说明作者认为什么重要）；
4. 只抄结构，不抄依赖版本——多数项目的 Spring Boot 版本比你用的旧。

## 9. 门禁汇总

| 门 | 判定方式 | 不过会怎样 |
| --- | --- | --- |
| G0 决策冻结 | 清单无“待定” | 反复选型，永远不开始 |
| G1 能启动能读库 | 7 张表 + 页面有数据 | 后面所有功能建在流沙上 |
| G2 权限生效 | 未登录 302、越权 403 | 数据泄露，返工所有接口 |
| G3 状态机可靠 | 42 组合测试 + 删转移会红 | 状态错乱，事件与状态不一致 |
| G4 交付可用 | 干净机器一条命令 + 重启不丢 | 只能在自己电脑上跑 |
