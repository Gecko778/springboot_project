## 1. 产品定位与版本路线

**一句话**：一个给中小团队内部使用的工单系统，把散落在群聊和口头里的请求，变成有状态、有责任人、有记录的条目。

终局目标是一个可商用的产品，但那是一年以后的事。当前只做 MVP——**先让一个小团队真的用它，而不是继续完善文档**。

| 版本 | 目标 | 核心内容 |
| --- | --- | --- |
| **V1.0（本次）** | 一个 5–10 人团队能真实用起来 | 提交、分派、处理、回复、关闭、权限、部署 |
| V1.1 | 用得顺手 | 站内通知、分类管理、附件、SLA 超时标红、看板 |
| V1.2 | 有亮点 | AI 分诊：分类建议 + 回复草稿 |
| V2.0 | 可对外售卖 | 多租户、计费、邮件入口、SSO、合规与备份 |
| 更远 | 商用加固 | 审计报表、开放 API、Webhook、帮助中心 |

这份文档只定义 **V1.0**。V1.1 及以后的内容写在第 4.2 节，**明确不做，但记着**。

---

## 2. MVP 的目标与成功标准

### 2.1 目标

跑通一个完整的闭环：**提交 → 分派 → 接单 → 处理 → 解决 → 确认关闭**，并且只有该看见的人能看见。

### 2.2 成功标准

- 一个没用过的人，不看说明书能在 2 分钟内提交一条工单。
- 处理人打开列表，一眼知道“哪些是我的、哪些最急”。
- 任意工单能看到完整过程：谁在什么时候改了什么、说了什么。
- 换一台干净的机器，一条命令能启动，重启后数据不丢。
- 整整一周用它处理真实请求，不需要退回微信群。

### 2.3 非目标（MVP 阶段不追求）

- 不追求好看，页面的目标是“能用”，不是“能看”。
- 不追求高并发，先服务 10 个人，不为 1 万人设计。
- 不追求功能多，**宁可少一个功能，也不要多一个半成品**。

## 3. 用户与角色

| 角色 | 代号 | 是谁 | 主要诉求 |
| --- | --- | --- | --- |
| 提交人 | `REPORTER` | 任何员工 | 快速提交、知道进度、能确认解决 |
| 处理人 | `AGENT` | IT / 行政 / 运维 | 清楚看到分给自己的活、按优先级处理 |
| 管理员 | `ADMIN` | 团队负责人 | 分派工作、看全貌、管账号 |

一个账号可以同时是提交人和处理人。角色由管理员分配；MVP 不做自定义角色。

### 3.1 验收用场景

- **A 报修**：提交（分类“硬件”、优先级“高”）→ 管理员分派给老王 → 老王接单 → 回复“下午来看” → 标记解决 → 提交人确认关闭。
- **B 追问**：提交三天没动静，提交人在工单里追问 → 管理员看到后完成分派。
- **C 撤销**：提交后发现是自己插错线，撤销工单（仅待分派/已分派可撤销）。
- **D 退回**：标记解决但没修好，提交人退回 → 工单回到处理中。

## 4. 范围

### 4.1 MVP 做（V1.0）

- 账号：自助注册、登录、查看当前用户；管理员改角色、停用账号
- 工单：创建、列表（按角色限权）、详情、编辑（限未分派）、撤销
- 流转：分派、接单、标记解决、确认关闭、退回
- 沟通：公开回复、内部备注、回复流
- 记录：工单事件时间线（状态变更、分派、回复全部留痕）
- 组织：预置分类（不做管理界面）；四档固定优先级
- 查找：按状态/分类/优先级/处理人筛选，标题关键字搜索，分页
- 界面：4 个页面（登录、工单列表、工单详情、新建工单）
- 交付：Docker Compose 一键启动、CI 自动测试

### 4.2 不做（按版本归档，防止项目膨胀）

| 延到 | 内容 |
| --- | --- |
| V1.1 | 站内通知与未读数、分类管理界面、附件、SLA 超时标红、统计看板、邮件通知 |
| V1.2 | AI 分类建议、AI 回复草稿、知识库 |
| V2.0 | 多租户、订阅计费、邮件转工单、SSO/LDAP、开放 API 与 Webhook、数据导出与删除、备份恢复演练 |
| 永不（本项目） | 移动端 App、实时聊天、子工单/工单合并、多级审批流 |

## 5. 核心流程

### 5.1 状态机（本系统最不能写错的部分）

| 当前状态 | 动作 | 目标状态 | 谁能做 |
| --- | --- | --- | --- |
| 待分派 `NEW` | 分派 | 已分派 `ASSIGNED` | 管理员 |
| 待分派 `NEW` | 撤销 | 已撤销 `CANCELLED` | 提交人 |
| 已分派 `ASSIGNED` | 接单 | 处理中 `IN_PROGRESS` | 该工单处理人 |
| 已分派 `ASSIGNED` | 改派 | 已分派 `ASSIGNED` | 管理员 |
| 已分派 `ASSIGNED` | 撤销 | 已撤销 `CANCELLED` | 提交人 |
| 处理中 `IN_PROGRESS` | 标记解决 | 待确认 `RESOLVED` | 该工单处理人 |
| 处理中 `IN_PROGRESS` | 改派 | 已分派 `ASSIGNED` | 管理员 |
| 待确认 `RESOLVED` | 确认 | 已关闭 `CLOSED` | 提交人 |
| 待确认 `RESOLVED` | 退回 | 处理中 `IN_PROGRESS` | 提交人 |
| 已关闭 `CLOSED` | 重开 | 处理中 `IN_PROGRESS` | 提交人 |

**规则**：
1. 不在上表中的跳转，后端一律拒绝（前端藏按钮不算）。
2. `CANCELLED` 是终态。
3. 每次状态变更都要写一条事件记录，包含操作人、动作、前后状态、时间。
4. 同一工单被两人同时操作时，后提交者得到明确冲突提示，而不是静默覆盖。

### 5.2 编号

`TK-YYYYMMDD-NNNN`，例如 `TK-20261116-0001`，按天重置，全局唯一，不可修改。

## 6. 功能需求（V1.0）

### 6.1 账号

| 编号 | 需求 | 验收标准 |
| --- | --- | --- |
| FR-01 | 注册 | 用户名唯一（4–32 位字母数字）、密码 ≥8 位、显示名必填；注册后角色为 `REPORTER` |
| FR-02 | 登录 | 用户名+密码；成功返回访问令牌；失败提示统一为“用户名或密码错误” |
| FR-03 | 当前用户 | 返回用户名、显示名、角色；绝不下发密码哈希 |
| FR-04 | 改角色 | 仅管理员；不能把最后一个管理员降级 |
| FR-05 | 停用账号 | 仅管理员；停用后无法登录；其名下未完成工单需先转交才能停用 |

### 6.2 工单

| 编号 | 需求 | 验收标准 |
| --- | --- | --- |
| FR-10 | 创建 | 标题 5–100 字，描述 10–2000 字，分类必填，优先级默认“普通”；返回编号，状态 `NEW` |
| FR-11 | 列表 | 分页；提交人只见自己的，处理人只见分派给自己的，管理员见全部；支持状态/分类/优先级/处理人筛选与标题搜索 |
| FR-12 | 详情 | 返回全部字段、当前状态、当前用户可执行的动作列表、回复流、事件时间线 |
| FR-13 | 编辑 | 仅提交人且仅 `NEW` 状态；可改标题/描述/分类/优先级 |
| FR-14 | 撤销 | 仅提交人，仅 `NEW`/`ASSIGNED`；不可恢复 |
| FR-15 | 分派 | 仅管理员；只能分派给启用中的 `AGENT`/`ADMIN` |
| FR-16 | 接单 | 仅该工单处理人；`ASSIGNED` → `IN_PROGRESS` |
| FR-17 | 标记解决 | 仅该工单处理人；必须填写 ≥10 字解决说明 |
| FR-18 | 确认关闭 | 仅提交人；`RESOLVED` → `CLOSED` |
| FR-19 | 退回 | 仅提交人；必须填写退回原因；`RESOLVED` → `IN_PROGRESS` |
| FR-20 | 重开 | 仅提交人；`CLOSED` → `IN_PROGRESS` |

### 6.3 沟通

| 编号 | 需求 | 验收标准 |
| --- | --- | --- |
| FR-30 | 公开回复 | 参与方均可；不改变状态 |
| FR-31 | 内部备注 | 仅 `AGENT`/`ADMIN`；提交人查询回复流时**完全不可见**（不是前端隐藏） |
| FR-32 | 回复流 | 按时间正序，含作者、角色、类型、时间；内部备注有明显标记 |

### 6.4 页面（4 个）

| 编号 | 页面 | 内容 |
| --- | --- | --- |
| FR-40 | 登录页 | 登录表单；注册入口 |
| FR-41 | 工单列表 | 当前用户可见范围内的工单，筛选与分页，一行内能看到状态与处理人 |
| FR-42 | 新建工单 | 标题、描述、分类、优先级 |
| FR-43 | 工单详情 | 字段、状态、回复流、回复框、按角色显示的动作按钮 |

## 7. 权限矩阵

| 功能 | 提交人 | 处理人 | 管理员 |
| --- | --- | --- | --- |
| 创建工单 | ✅ | ✅ | ✅ |
| 查看自己的工单 | ✅ | ✅ | ✅ |
| 查看分派给自己的工单 | — | ✅ | ✅ |
| 查看全部工单 | ❌ | ❌ | ✅ |
| 编辑（仅 `NEW`） | ✅ 自己的 | ❌ | ✅ |
| 分派 / 改派 | ❌ | ❌ | ✅ |
| 接单 / 标记解决 | ❌ | ✅ 自己的 | ✅ |
| 确认 / 退回 / 重开 | ✅ 自己的 | ❌ | ❌ |
| 公开回复 | ✅ 自己的 | ✅ 自己的 | ✅ |
| 内部备注 | ❌ | ✅ 自己的 | ✅ |
| 改角色 / 停用账号 | ❌ | ❌ | ✅ |

> 越权统一返回 `403`，且不泄露“该资源是否存在”。

## 8. 不可延后的架构约束

这几条现在做只要几小时，以后补要重写。**MVP 功能可以砍，这七条不能砍。**

| 编号 | 约束 | 为什么现在就得有 |
| --- | --- | --- |
| A-01 | 所有业务表带 `org_id`（MVP 固定为 1） | V2 改多租户时，不用回头改每一张表和每一个查询 |
| A-02 | 用迁移工具管理数据库结构（Flyway） | 手改表结构，上线后再也追不清哪台机器是什么版本 |
| A-03 | 状态流转集中在一处（状态机类） | 散落在各个 Service 里，加一个状态就要翻遍代码 |
| A-04 | 权限校验集中在服务层，不写在 Controller | 分散判断必漏，且无法统一测试 |
| A-05 | 工单所有变更写事件表（审计） | 事后补审计只能补“以后”，历史过程永远丢失 |
| A-06 | 配置全部走环境变量，密钥不进代码库 | 密钥一旦进过 Git，就等于泄露 |
| A-07 | 统一错误码与错误响应格式 | 前端和排查都依赖它，后期改会牵连所有接口 |

## 9. 非功能需求（MVP 级）

| 编号 | 类别 | 要求 |
| --- | --- | --- |
| NFR-01 | 性能 | 1 万条工单规模，列表 P95 < 500ms，详情 P95 < 200ms |
| NFR-02 | 并发 | 同一工单并发操作不得产生非法状态（乐观锁） |
| NFR-03 | 安全 | 密码 BCrypt；令牌有过期时间；越权 403；查询全部参数化 |
| NFR-04 | 可观测 | 每个请求有 `traceId`，提供健康检查接口 |
| NFR-05 | 可维护 | 分层清晰；统一异常处理；关键业务规则有注释说明“为什么” |
| NFR-06 | 可测试 | 状态机规则单元测试覆盖全部合法与非法跳转；核心接口有集成测试 |
| NFR-07 | 可部署 | Docker Compose 一条命令启动应用与数据库；重启数据不丢 |

## 10. 里程碑

不设时间表，按依赖顺序完成即可。每一步的验收标准必须满足才能进入下一步。

| 里程碑 | 内容 | 完成标志 |
| --- | --- | --- |
| M1 骨架与数据 | 项目初始化、分层、Flyway 迁移、实体与 MyBatis Mapper、工单列表页 | 浏览器能看到从数据库读出的工单 |
| M2 身份与权限 | 表单登录、注册、角色、数据范围控制、管理员用户页 | 未登录跳转；三种角色可见范围正确；越权 403 |
| M3 业务闭环 | 状态机、7 个流转动作、回复与内部备注、事件时间线、乐观锁 | 场景 A–D 全部走通；非法跳转返回 409 |
| M4 质量与交付 | 单元测试、Testcontainers 集成测试、CI、镜像、部署 | 干净机器一条命令启动；CI 全绿；重启数据不丢 |

## 11. 验收清单（Definition of Done）

- [ ] 三种角色分别登录，可见数据范围正确
- [ ] 场景 A–D 全部走通
- [ ] 所有非法状态跳转被后端拒绝，且有测试证明
- [ ] 提交人看不到内部备注；处理人看不到他人未分派给自己的工单
- [ ] 每条工单可查看完整事件时间线
- [ ] 列表筛选、搜索、分页可用
- [ ] 本地一条命令跑完测试；CI 中同样通过
- [ ] 干净机器一条命令启动，重启后数据不丢
- [ ] 密钥未出现在代码库与镜像中

## 12. 风险

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 又想加功能 | 永远做不完 | 严格执行第 4.2 节，新想法一律记到 V1.1 |
| 状态机写散 | 后期崩 | A-03，集中 + 全覆盖测试 |
| 权限漏判 | 数据泄露 | A-04，服务层统一校验 + 越权测试用例 |
| 页面拖时间 | 交付延期 | 页面只求能用，样式统一用一套现成 CSS |
| 环境耗时 | 学不到东西 | 用 Docker，不在本地装数据库 |
