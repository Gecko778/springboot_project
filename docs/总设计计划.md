## 0. 本文回答什么

`02-design.md` 回答“表怎么建、接口怎么排”，本文回答三个更上层的问题：

1. 这套系统整体长什么样，为什么是这个形状；
2. 每个关键技术选择，放弃了什么，代价是什么；
3. 哪些东西现在不做，什么条件下才做。

**判断标准**：本文里每一条决策，都应该能回答“如果不这么做，会在什么时候付出什么代价”。

## 1. 调研：读了什么，得出什么

### 1.1 调研清单

| 项目 | 规模 | 借鉴什么 | 不借鉴什么 |
| --- | --- | --- | --- |
| [spring-petclinic](https://github.com/spring-projects/spring-petclinic) | ★9.7k | Controller/Service/Repository 的最小清晰分层；用 Testcontainers 做集成测试 | 过于简单，没有权限与并发 |
| [spring-boot-realworld-example-app](https://github.com/gothinkster/spring-boot-realworld-example-app) | ★1.6k | **四层结构**（api/application/core/infrastructure）；Command/Query 分离；MyBatis XML 写法 | 依赖版本陈旧（`javax.*`、joda-time），只借结构不借代码 |
| [macrozheng/mall](https://github.com/macrozheng/mall) | ★85k | 多模块拆分（common/security/admin/portal）；安全模块独立 | MyBatis Generator 生成 POJO；对单人项目过重 |
| [RuoYi-Vue](https://github.com/yangzongzhuan/RuoYi-Vue) | ★3.3k | 权限注解 `@PreAuthorize("@ss.hasPermi(...)")`；`@Log` + AOP 操作审计；统一响应与分页对象 | 菜单级权限体系（权限表+角色权限+菜单表），MVP 用不上 |
| [RuoYi-Vue-Plus](https://github.com/dromara/RuoYi-Vue-Plus) | ★2.9k | **BO/VO 分离**；把 MyBatis 公共能力收敛成一个 common 模块；多租户插件 | 工作流引擎、多租户插件（V2 再说） |
| [eladmin](https://github.com/elunez/eladmin) | ★21.9k | DTO + MapStruct 的转换层写法 | JPA + 大量代码生成，与本项目技术栈相反 |
| [halo](https://github.com/halo-dev/halo) | ★40k | 按领域分包（content/security/notification）；`infra/exception` 单独收敛；扩展点设计 | 插件化架构，MVP 不需要 |
| [spring-modulith](https://github.com/spring-projects/spring-modulith) | ★1.2k | “模块化单体”的验证思路：模块边界可以用测试守住 | 现阶段不引入框架，先靠包结构和 review 约束 |
| [zammad](https://github.com/zammad/zammad) | ★6.1k | **领域模型**：`audit_log`、`history`、`activity_stream`、`knowledge_base`、`macro`、`trigger`、`sla`、`data_privacy_task`；AI agent 分为分类/定级/打标/改标题几种 | Ruby 实现与 Rails 约定 |
| [osTicket](https://github.com/osTicket/osTicket) | ★4k | 工单渠道（邮件/表单/API）的产品形态 | PHP 实现 |

### 1.2 三条结论

**结论一：Java 侧缺“工单系统”参考，缺的是“后台脚手架”。**
RuoYi、mall、eladmin 都是通用后台，它们的复杂度来自“什么业务都能装”，不是来自工单。照搬会得到一堆用不上的菜单、权限、代码生成器。**该借的是它们的工程习惯（审计、统一响应、权限注解），不是它们的体量。**

**结论二：好的 Java 项目都是“按领域分包”，不是“按技术层分包”。**
RealWorld 是 `api / application / core / infrastructure`，halo 是 `content / security / notification / theme`。反面教材是把所有 Controller 放一个包、所有 Service 放一个包——文件超过 30 个就找不到东西。本项目采用“功能包 + 包内分层”。

**结论三：工单系统的真正难点在领域，不在框架。**
Zammad 用 40 多个模型才把工单、组、角色、SLA、触发器、宏、知识库说清楚。我们的 MVP 只取其中 7 张表，但**状态机、事件流、权限归属**这三件事必须做对，否则后面加什么功能都是歪的。

## 2. 架构决策

每条格式：**结论 / 理由 / 放弃的方案 / 代价**。

### D1 模块化单体，不做微服务

- **结论**：一个 Spring Boot 进程，内部按模块划边界。
- **理由**：单人项目，微服务带来的部署、链路追踪、分布式事务成本远大于收益；RuoYi、mall 这类被大量使用的系统也都是单体（mall 是单应用多模块）。
- **放弃**：Spring Cloud、服务拆分、消息队列。
- **代价**：将来真要拆，需要先把模块边界理清楚——所以现在就用包结构和依赖规则把边界画出来。

### D2 单个 Maven 模块，按功能分包

- **结论**：不拆 `mall-common`、`ruoyi-system` 这种多模块，全部在一个 `src/main/java` 下按 `ticket/`、`user/`、`auth/` 分包。
- **理由**：多模块的价值是“团队并行 + 依赖隔离”，单人项目只会多出 `pom` 维护和跨模块跳转成本。
- **放弃**：Maven 多模块、Gradle 多项目。
- **代价**：模块边界靠约定而非编译期强制。缓解办法：包之间只允许单向依赖（见第 3 节），review 时检查。

### D3 四层结构：api / application / domain / infrastructure

- **结论**：

```
api             Controller、表单对象、视图对象
application     Service（事务、权限、编排）、QueryService
domain          实体、枚举、状态机（纯 Java，无 Spring 依赖）
infrastructure  Mapper 接口 + XML、外部集成
```

- **理由**：借 RealWorld 的结构。它把“读”和“写”分开（QueryService 直接返回读模型），避免了实体泄露到模板、也避免为了展示去拼装一堆关联。
- **放弃**：经典三层（Controller-Service-Repository 平铺）。三层在第 20 个类之后开始混乱。
- **代价**：比三层多一层概念，新手前期会觉得“为什么查个列表还要两个类”。

### D4 轻量读写分离（不是 CQRS 框架）

- **结论**：写操作走 `XxxService`（事务 + 状态机 + 事件），读操作走 `XxxQueryService`（直接返回视图对象，不返回实体）。
- **理由**：工单详情要拼“字段 + 可执行动作 + 回复流 + 时间线”，用实体拼会在模板里触发一堆查询；查询服务一次拼好，模板只负责渲染。
- **放弃**：完整 CQRS（命令总线、事件溯源、读写库分离）。
- **代价**：同一个概念会有两个类（`TicketService` / `TicketQueryService`），需要接受这点重复。

### D5 MyBatis 手写 SQL，不用 MyBatis-Plus

- **结论**：Mapper 接口 + XML，SQL 全部手写，分页手写 `limit/offset` + `count`。
- **理由**：学习期最重要的是“看得见 SQL”。RealWorld 的 XML 写法（`<if>`、`<set>`、`#{obj.field}`）已经足够表达；Plus 的 `LambdaQueryWrapper` 会把 SQL 藏起来，出问题只能猜。
- **放弃**：MyBatis-Plus、MyBatis Generator、Spring Data JPA。
- **代价**：CRUD 模板代码变多。**切换条件**：当 Mapper 里纯 CRUD 方法超过总方法数的 40%，再评估引入 Plus（它可与原生 MyBatis 共存）。

### D6 状态机用“转移表 + 一个类”

- **结论**：枚举 + `Map<Key, Transition>`，`require()` 校验合法性，`isAllowed()` 供页面生成按钮。
- **理由**：RuoYi 那类系统把状态判断散在 Service 里，加一个状态要全局搜索。集中一处后，状态机可以被参数化测试完整覆盖（42 种组合）。
- **放弃**：Spring StateMachine（对 6 个状态过重）、工作流引擎（Flowable/Activiti）。
- **代价**：复杂流程（多级审批、会签）表达不了。**触发条件**：当出现“按部门走不同审批链”的需求时，再评估引入 Flowable。

### D7 事件表做审计与时间线

- **结论**：`ticket_event` 记录每一次状态变更、分派、回复，`detail` 用 JSON 存上下文。
- **理由**：Zammad 同时有 `history`（字段级变更）和 `audit_log`（操作审计），说明这两件事在生产系统里是刚需。我们用一张表同时满足“时间线展示”和“审计追溯”。
- **放弃**：只打应用日志、用 AOP 统一记日志（RuoYi 的 `@Log` 方式）。
- **代价**：写操作多一次插入。**注意**：事件写入必须和业务变更在同一事务里，否则会出现“状态变了但没记录”。

### D8 权限 = 角色 + 资源归属，不用权限字符串

- **结论**：三个角色枚举 + Service 层判断“这条工单是不是你的”。
- **理由**：RuoYi 的 `system:user:add` 权限串是为“菜单/按钮级细粒度授权”设计的，需要权限表、角色权限表、菜单表三张表配合。MVP 只有三种角色，用不上；但升级路径要留：将来加 `permission` 表 + `@PreAuthorize`，Service 层判断可以保留。
- **放弃**：RBAC 全套（权限表、菜单表、数据范围注解）。
- **代价**：新增角色要改代码而不是改配置。**触发条件**：出现“客户要自定义角色”时再上 RBAC。

### D9 认证用 Session，不用 JWT

- **结论**：Spring Security 表单登录 + 服务端 Session。
- **理由**：页面是服务端渲染，Session 天然适配；CSRF、会话固定攻击防护、登出失效都是框架自带。JWT 在这个场景要自己解决令牌存放、续期、撤销，纯负担。
- **放弃**：JWT、OAuth2、SSO。
- **代价**：将来做移动端/开放 API 时要补一套 Token 认证（两者可按路径前缀共存）。

### D10 Flyway 是表结构的唯一事实

- **结论**：所有 DDL 走 `db/migration/V*.sql`，禁止手工改库、禁止 `ddl-auto`。
- **理由**：RuoYi/mall 这类项目常带一份巨大的 `sql/ry_2024.sql` 初始化脚本，升级靠人肉对比。Flyway 让“这台机器是什么版本”变成可查询的事实。
- **放弃**：Hibernate 自动建表、手工执行 SQL。
- **代价**：改表要多写一个迁移文件；已经执行过的迁移不能改（只能新增）。

### D11 多租户预留：所有业务表带 `org_id`

- **结论**：MVP 只有一条 org 记录，但表结构、查询、权限都按“有租户”写。
- **理由**：RuoYi-Vue-Plus、lamp-cloud 都证明了后补租户字段的代价——要改每一张表、每一条 SQL、每一个唯一索引。
- **放弃**：现在就做租户隔离（独立 schema、租户路由）。
- **代价**：每条 SQL 多一个 `org_id` 条件，容易漏。缓解：所有查询方法第一个参数固定是 `orgId`，review 时一眼能看出漏没漏。

### D12 AI 只建议，不执行；可整体关闭

- **结论**：AI 输出只作为“建议”展示，写操作必须由人点击；配置开关可关闭全部 AI 功能；模型不可用时主流程不受影响。
- **理由**：Zammad 的 AI 能力也设计成 `ticket_categorizer`、`ticket_prioritizer` 这类“建议型 agent”，而不是自动改数据。商用系统里，AI 出错的责任必须有人兜。
- **放弃**：自动分派、自动回复、自动关单。
- **代价**：体验上不如“全自动”惊艳。

## 3. 模块划分与依赖规则

```
        ┌─────────────┐
        │     api     │  Controller / Form / ViewModel
        └──────┬──────┘
               │ 只能向下
        ┌──────▼──────┐
        │ application │  Service / QueryService（事务、权限、编排）
        └──────┬──────┘
               │
     ┌─────────┴─────────┐
     ▼                   ▼
┌─────────┐      ┌───────────────┐
│ domain  │      │infrastructure │  Mapper + XML
└─────────┘      └───────────────┘
```

| 规则 | 违反的典型症状 |
| --- | --- |
| `api` 不直接依赖 `infrastructure` | Controller 里出现 `TicketMapper` |
| `domain` 不依赖任何层，也不依赖 Spring | 状态机里出现 `@Service`、`@Autowired` |
| `application` 不返回实体给 `api` | 模板里访问实体的关联字段 |
| 跨功能包只允许单向依赖（`ticket → user`，不允许反向） | `user` 包里 import 了 `ticket` 的类 |
| SQL 只在 `infrastructure` 的 XML 里 | Java 字符串里出现 `select * from` |

## 4. 领域模型

### 4.1 聚合边界

| 聚合 | 根 | 内部对象 | 不变式 |
| --- | --- | --- | --- |
| 工单 | `Ticket` | 无（回复与事件是独立聚合，按 ticketId 关联） | 状态只能按转移表变化；`CLOSED` 后除重开外不可改 |
| 用户 | `User` | 无 | 用户名在组织内唯一；停用前必须转交未完成工单 |
| 分类 | `Category` | 无 | 有工单引用时不可删除，只能停用 |

回复与事件不放进 `Ticket` 聚合内部，是为了避免“打开一条工单要把所有回复都加载进来”。代价是**跨聚合的一致性要靠事务**保证（同一事务里写 ticket 和 event）。

### 4.2 从 Zammad 借来的、但 MVP 不做的模型

| 模型 | 作用 | 什么时候需要 |
| --- | --- | --- |
| `group`（组） | 工单按团队分流 | 出现“多个处理团队”时 |
| `sla` | 响应/解决时限 + 升级链 | V1.1 |
| `macro` / `trigger` | 预设回复、自动动作 | 出现“重复操作太多”时 |
| `knowledge_base` | 知识库 | V1.2（AI 检索的数据源） |
| `data_privacy_task` | 数据导出/删除请求 | V2（合规） |

## 5. 数据与并发原则

1. **时间统一 UTC 存储**，展示时转本地时区；不用数据库默认时区。
2. **并发用乐观锁**（`version` 条件更新），不用悲观锁——工单冲突概率低，锁反而容易卡死。
3. **编号用取号表**，不用 `count(*) + 1`，避免并发撞号。
4. **索引跟着查询走**：列表按 `(org_id, status, updated_at)`，分派列表按 `(org_id, assignee_id, status)`。
5. **不做物理删除**：用户停用、分类停用，工单永不删。

---

## 6. 接口与交互原则

1. **表单 + 重定向（PRG）**，MVP 不提供 JSON API。
2. **状态变更用动词端点**（`POST /tickets/{id}/accept`），不用 `PATCH` 改字段。
3. **按钮显隐与后端校验共用同一份规则**（`isAllowed`）。
4. **错误页说人话**：发生了什么 + 你能做什么，不显示堆栈。
5. **越权统一 403**，不泄露资源是否存在。

## 7. 质量属性与手段

| 属性 | 手段 | 验证方式 |
| --- | --- | --- |
| 正确性 | 状态机参数化测试、集成测试跑完整链路 | `./mvnw verify` |
| 安全 | BCrypt、CSRF、越权校验、`#{}` 预编译 | 越权用例 + 代码 review |
| 可维护 | 四层结构、功能分包、依赖规则 | review 检查 import |
| 可观测 | 结构化日志 + `traceId` + `/actuator/health` | 部署后 `curl` |
| 可部署 | 多阶段镜像 + compose + 环境变量 | 干净机器一条命令 |
| 性能 | 索引 + 分页 + 避免 N+1 | 1 万条数据下测 P95 |

## 8. 演进路线与架构变化

| 版本 | 加什么 | 架构上要动什么 |
| --- | --- | --- |
| V1.0 | 闭环工单 | —（本文描述的就是它） |
| V1.1 | 通知、附件、SLA、看板 | 加 `notification` 表；附件引入对象存储；定时任务扫描超时 |
| V1.2 | AI 分诊 | 引入 Spring AI；向量检索（可先用 MySQL 全文索引起步）；AI 结果单独存表，不进主流程 |
| V2.0 | 多租户、计费、邮件入口、SSO | 租户路由与隔离策略；计费模块；邮件解析（IMAP）作为独立入口 |
| 更远 | 开放 API、Webhook | 引入 Token 认证与 API 版本管理 |

**原则**：每次升级只动一个维度。V1.2 加 AI 时不碰租户，V2.0 加租户时不碰 AI。

## 9. 刻意不做的事

| 不做 | 理由 |
| --- | --- |
| 代码生成器（MBG） | 生成一次就再也看不懂，学习期最忌讳 |
| 低代码平台 | 需求是学 Spring Boot，不是学配置 |
| 工作流引擎 | 6 个状态的流程用引擎是杀鸡用牛刀 |
| 微服务 / 消息队列 | 单进程能解决的事，不引入分布式复杂度 |
| Redis 缓存 | 1 万条数据 MySQL 足够；缓存会引入一致性新问题 |
| 前端框架 | Thymeleaf 够用，学的是后端 |
| 完整 RBAC | 三角色用不上，等客户提需求 |

## 10. 风险与未决

| 风险 | 触发信号 | 对策 |
| --- | --- | --- |
| MyBatis 与 Spring Boot 4 版本不匹配 | 启动报 `NoSuchMethodError`、自动配置不生效 | 锁定 starter 4.1.x 对应 Boot 4.1.x |
| 模板越来越胖 | `detail.html` 超过 150 行 | 拆 fragment，逻辑前移到视图对象 |
| 状态机与按钮不同步 | 页面出现点了会 409 的按钮 | 按钮只从 `isAllowed` 生成 |
| 过度设计 | 写一个功能要改 6 个类 | 回到“能不能少一层” |
| 功能膨胀 | 开始想加“顺便也支持一下…” | 记到 V1.1 清单，不进当前版本 |

**未决**：
1. Session 认证是否最终确认（见 `02-design.md` 第 11 节）。
2. AI 分诊的模型来源（本地 Ollama / 云 API），到 V1.2 再定，但要在 V1.0 就避免把工单正文散落到各处，便于将来统一脱敏。
